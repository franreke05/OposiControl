# Security

`SEC-001: CLOSED / VERIFIED_FOR_CANONICAL_BACKEND_SCOPE`.

The canonical scope has service-role-only writers for `record_answer`, `record_event` and `admin_grant_tickets`, empty `search_path`, no client execution grants and Ktor error mapping for known domain failures. Wallet retry, payload-conflict and concurrency behavior passed controlled MAIN tests. Canonical admin routes require a verified admin JWT; the static token is isolated to local development legacy `/admin/*` and `/content/*` surfaces and is no longer embedded in client builds.

Admin client session (audit loop 6, MASTER6-AUTH-001..005/012): the Supabase refresh token is kept in memory only; `session_cache` stores the short-lived access token with an empty `refresh_token` column, and legacy rows are scrubbed on open, so a restarted app resumes only until that access token expires. Refreshes are single-flight, run before expiry and once on a backend 401 (`installAdminSessionRefresh`), and a late login/refresh that finishes after logout is discarded and revoked. Only a definitive Auth rejection (4xx except 408/425/429) clears the session; offline, timeouts, 5xx and 429 keep it. Logout clears locally first, then revokes with `scope=local`, refreshing once if the access token has expired, and reports a non-blocking failure if the server did not confirm. On desktop a present-but-blank `-Doposi.BACKEND_TOKEN=` is authoritative: no env var or `.env` value can reintroduce the static token.
Desktop SQLite is opened with `secure_delete=ON` on every connection (`openHardenedDesktopDriver`), so the legacy refresh token deleted by the scrub is zero-filled rather than left in free pages, and on POSIX file systems the DB directory is set to 0700 and the file to 0600 (Windows relies on the inherited per-user ACL of %APPDATA%). The 0700/0600 assertions are Assume-guarded (skipped on Windows, where only the portable no-op part runs) and execute in CI on ubuntu-latest via `:core:database:jvmTest`. Not covered: the Android and iOS drivers do not set secure_delete; pages freed by deletes made by earlier builds (before upgrade), copies in the rollback journal, OS backups or filesystem snapshots cannot be scrubbed from inside the app; the short-lived access token is still stored in plaintext (an OS secret store would need a new dependency).

Desktop DB hardening (MASTER7-AUTH-002/SEC-001): after migration the legacy working-directory DB is scrubbed (refresh_token blanked with `secure_delete`, other rows kept) or deleted if unreadable, on every start; the app-data directory is made 0700 before the DB or legacy copy is placed in it, and a failed owner-only hardening is logged at WARN instead of being swallowed.

Supply chain (MASTER7-CICD-001/002/005, verification only, no secrets): CI runs a gitleaks `secret-scan` over the full history, an OSV `dependency-audit` over the resolved runtime classpath, builds and boots the backend image (`backend-image`: uid 10001, read-only `/app`, `/health/live`), and Gradle verifies every artifact against `gradle/verification-metadata.xml` (sha256, strict). The OpenAPI lint tool is locked by `tools/redocly/package-lock.json`. `.github/dependabot.yml` only proposes updates. If the repository moves to an organization, gitleaks-action needs a `GITLEAKS_LICENSE` secret (external setting, not created here).

The client login bypass is closed (`TEMPORARILY_DISABLE_LOGIN = false`). `AppV1Gateway.hasAdminRole` uses the canonical `superadmin`/`admin` role set from `roles_usuario` + `roles_app`; moderator remains a separate role and is not promoted to admin.

Service-role and auth-secret references remain in backend gateways/configuration; no service-role reference was observed in client modules. The backend is the intended trust boundary, so route authorization and ownership filters are critical. `OPOSICONTROL_BACKEND_TOKEN` is temporary/legacy and `OPOSICONTROL_ALLOW_DEV_USER`/`OPOSICONTROL_ALLOW_DEV_TOKEN` are dev/test-only controls, not production authorization.

Content negotiation, authentication and status pages are installed. OposiBots auth has its own rate limiting and request IDs; there is no global Ktor `CallLogging`, no tracing, no global rate limit and no verified global CORS/HSTS policy. Prometheus `/metrics` does exist (D8-09, `installBackendPrometheusMetrics`, `PrometheusMetrics.kt`): `METRICS_ENABLED=false` answers 404 and, when `METRICS_SCRAPE_TOKEN` is set, it requires `Authorization: Bearer <token>` (constant-time compare, `Cache-Control: no-store`); with an empty token the scrape is open (B-22) and the proxy blocks `/metrics` externally (`ops/caddy/metrics-block.caddy`). HTTPS/proxy controls are conditional in OposiBots configuration.

The current MAIN scope was verified through Supabase read checks and controlled fixtures; the fixture rows were removed. Full Storage, deployment/proxy and legacy-schema coverage remains `NOT_VERIFIED`.

Remaining external blockers are valid non-personal Auth E2E evidence, complete live Storage policy/object verification and unrelated legacy RPC/consumer reconciliation. They do not alter the closed canonical backend boundary and were not changed in this gate.
