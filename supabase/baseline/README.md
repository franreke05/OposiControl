# supabase/baseline: CI PostgreSQL 17 gate (DB-CI-PG17)

These files are the input to the `db-pg17` job in `.github/workflows/ci.yml` (`scripts/db-pg17-gate.sh`). They are not migrations and are never deployed.

| File | What it is |
|---|---|
| `MAIN_MIGRATION_HISTORY.txt` | The REAL migration history of MAIN (`supabase_migrations.schema_migrations`: version + name), read READ-ONLY on 2026-10-14 (77 versions, last `20261015100000`). The reference of the gate. |
| `PENDING_MIGRATIONS.txt` | The migrations of the repo that MAIN does not have yet. The gate fails unless it equals exactly the files of `supabase/migrations` whose version is not in `MAIN_MIGRATION_HISTORY.txt`, minus the known history divergences (`HISTORY_DIVERGENT` in `scripts/db-pg17-gate.sh`): `20260923103000_news_canvas_schema` (applied on MAIN as `20260923090948`) and `20260730120000_oposibots_auth_profile_rls` (never recorded; its content is `20260803092306`). On 2026-10-14 the only pending migration is `20261016100000_slice3_attempt_content_revisions`; every Slice 0/1/2/3/7 and `security_*` migration is applied on MAIN. The per-slice manifests are checked by `verify-migrations-manifest.sh`. |
| `main_shape_subset.sql` | Generated by `scripts/db-pg17-bootstrap-extract.mjs`; do not edit it by hand. It is the MAIN catalog DDL, with no rows, for **only** the objects the gate needs: the closure of what the pending migrations AND `assertions.sql` name (FK targets, trigger and policy functions, and the tables and functions named qualified inside included function bodies). Its header lists them. It also carries their constraints, FKs, indexes, RLS, policies, triggers, grants and comments, the schemas and extensions, and the default privileges `FOR ROLE postgres`. Statements are copied verbatim from the read-only MAIN catalog capture of the same date as the history. |
| `main_shape_subset_20260929.sql` | FROZEN copy of the subset generated from the 2026-09-29 capture (MAIN BEFORE Slice 0/1/2/3/7). Used ONLY by `backend/dbtest` (Slice3Db), whose migration tests apply those migrations on the shape they were written against. Never regenerated. |
| `assertions.sql` | A versioned copy of the local gate's `local_assertions.sql`: behaviour checks in one transaction that ends in ROLLBACK, plus a grants/RLS matrix. Changes, commented in the file: MASTER-DB-001 made `username` server-owned; since 2026-10-14 the Slice 3 block asserts the frozen set of 20261010100000 (annulled questions included) and the revision binding and DEC-015 reveal of 20261016100000. |

## Regenerating `main_shape_subset.sql`

Regenerate it only from a fresh **read-only** catalog capture of MAIN. The capture stays outside the repo (`C:\Users\franr\.oposibots-gate\baseline-<date>\`).

1. Run `scripts/db-main-catalog-capture.sql` on MAIN in a read-only session (2026-10-14: the `execute_sql` tool of the Supabase MCP). It sets the session `search_path` and runs ONE `SELECT` over `pg_catalog` only: no data rows, no DDL/DML, no secrets.
2. `node scripts/db-main-catalog-assemble.mjs <result> > <capture dir>/baseline_main.sql` (sections 01..10 in order).
3. Read the history (`supabase_migrations.schema_migrations`, version + name only, or the MCP `list_migrations`) into `MAIN_MIGRATION_HISTORY.txt`, and set `PENDING_MIGRATIONS.txt` to the repo migrations missing from it.
4. `node scripts/db-pg17-bootstrap-extract.mjs <capture dir>/baseline_main.sql > supabase/baseline/main_shape_subset.sql`, then `bash scripts/db-pg17-gate.sh` and `bash scripts/db-pg17-gate.test.sh`.

Also regenerate it whenever `PENDING_MIGRATIONS.txt` or `assertions.sql` changes, because the closure depends on what they name. The extraction is deterministic, and `scripts/db-pg17-bootstrap-extract.test.mjs` tests it.

The `ALTER DEFAULT PRIVILEGES FOR ROLE supabase_admin` statements are omitted. The local `postgres` role cannot run them, and the image already provides them. Errors are never allowlisted: the bootstrap loads with `ON_ERROR_STOP=1` in one transaction.

## Why a subset and not the full MAIN baseline

Committing the full MAIN baseline (about 100 tables, every function, policy and grant) is an OWNER decision that is still pending (ci_validation DB-CI-PG17, risk 1). The two MAIN-history divergences above are documented, not resolved (owner).

The subset follows the precedent the repo already accepts: `backend/dbtest` commits hand-copied MAIN shapes in `Slice0Db.PREREQUISITOS` and `Slice1Db.MAIN_SHAPES`.

## What the CI gate covers

- The real engine: Supabase `postgres` 17.6.1.171, pinned by digest. It provides the `auth` schema and `auth.uid()`, plus the `anon`, `authenticated` and `service_role` roles.
- The MAIN shape of every object the pending set touches, loaded with zero errors tolerated.
- The pending set applied in order with `ON_ERROR_STOP=1`. Each migration's `VERIFY` block runs right after it, and every counter must be 0. An empty result or a missing block fails the gate. The one exception is `20260928100100`, which predates the VERIFY convention and is covered by the matrix below.
- Behavioural assertions: the state gate of the RPCs, onboarding and replay, deletion requests, the anon/authenticated boundaries, client guards and NO ACTION retention; Slice 3 exam runtime (start / answer / finish / abandon commands, frozen set, annulled questions, one open attempt, commands closed to clients) and its hardening (`20261008100200`: an attempt the start command did not create is not found by any command and never frozen, immutable command marker, exam-origin only, FK indexes); Slice 2 "my exams" collection read (`20261008100300`: union of valid grants and command attempts, published exams only, own rows only, keyset page, groups over the whole filtered set, closed to clients and open to `service_role`).
- The final grants/RLS matrix:
  - RLS is enabled on every table.
  - Server-only tables grant no client privilege.
  - Every SECURITY DEFINER function pins `search_path`.
  - No SECURITY DEFINER function is executable by clients, except the two MAIN RLS helpers.
  - `service_role` can execute the Slice 1 RPCs.
  - The `private` schema is closed to clients.
- Running every `ROLLBACK` block in reverse returns the catalog to the post-bootstrap state. Re-applying reproduces the same catalog, with VERIFY at 0 again. The catalog fingerprint covers columns, constraints, indexes, triggers, function signatures, flags and ACLs, policies, RLS and table ACLs; it does not cover function bodies.
- A negative control, `scripts/db-pg17-gate.test.sh`, runs in the same job. Each seeded violation must fail for its own reason:
  - a manifest line removed;
  - a missing VERIFY block;
  - a client grant (caught by the boundary assertions, the matrix and VERIFY);
  - a syntax error;
  - an incomplete rollback.

## What it does NOT cover

The complete local PG17 gate stays the stronger gate before a deploy. See `SLICE_1_PRODUCTION_GATE.md` in OposiBot.

- **Objects of MAIN outside the closure:** about 85 other tables, their functions, policies, triggers and storage/realtime. The CI gate cannot detect an interaction between a pending migration and an object it does not name.
- **The 55/55 fingerprint against `main_fingerprint.json`, and the structural schema diff** (`schemadiff.js`).
- **Drift between this subset and live MAIN.** CI cannot read MAIN, so freshness depends on the manual recapture described above.
- **Two-session concurrency.** It stays in `backend/dbtest`, which runs on embedded PostgreSQL 16.
- **REST/PostgREST and the Ktor end-to-end.**
- **Data-dependent behaviour on real rows** (the capture has none).
- **Supabase platform internals:** GoTrue migrations, storage-api and realtime.
