# supabase/baseline: CI PostgreSQL 17 gate (DB-CI-PG17)

These files are the input to the `db-pg17` job in `.github/workflows/ci.yml` (`scripts/db-pg17-gate.sh`). They are not migrations and are never deployed.

| File | What it is |
|---|---|
| `PENDING_MIGRATIONS.txt` | The deploy set on top of MAIN: `2026092810*` plus `2026093*` plus `202610*` (Slice 3, and Slice 2 for the files named `202610*_slice2_*`). The gate fails unless it equals exactly those files in `supabase/migrations`, its `2026093*` part equals `supabase/SLICE1_MIGRATIONS.txt`, its `202610*_slice2_*` part equals `supabase/SLICE2_MIGRATIONS.txt` and the rest of its `202610*` part equals `supabase/SLICE3_MIGRATIONS.txt`. `verify-migrations-manifest.sh` ties those manifests to the ranges and versions cited in `docs/engineering/DEPLOYMENT.md`. |
| `main_shape_subset.sql` | Generated by `scripts/db-pg17-bootstrap-extract.mjs`; do not edit it by hand. It is the MAIN catalog DDL, with no rows, for **only** the objects the pending set touches: 29 tables and 20 functions, listed in its header. It also carries their constraints, FKs, indexes, RLS, policies, triggers, grants and comments, the schemas and extensions, and the default privileges `FOR ROLE postgres`. Statements are copied verbatim from the read-only MAIN catalog capture used by the local gate. Capture comments, which contain the project ref, are not copied. |
| `assertions.sql` | A versioned copy of the local gate's `local_assertions.sql`: behaviour checks in one transaction that ends in ROLLBACK. It adds a grants/RLS matrix. One assertion was changed deliberately, as commented in the file: MASTER-DB-001 made `username` server-owned. |

## Regenerating `main_shape_subset.sql`

Regenerate it only from a fresh **read-only** catalog capture of MAIN, taken by the owner before a deploy. The capture stays outside the repo.

```
node scripts/db-pg17-bootstrap-extract.mjs <path>/baseline_main.sql > supabase/baseline/main_shape_subset.sql
```

Also regenerate it whenever `PENDING_MIGRATIONS.txt` changes, because the closure depends on what the pending migrations name. The extraction is deterministic, and `scripts/db-pg17-bootstrap-extract.test.mjs` tests it.

The 3 `ALTER DEFAULT PRIVILEGES FOR ROLE supabase_admin` statements are omitted. The local `postgres` role cannot run them, and the image already provides them. Errors are never allowlisted: the bootstrap loads with `ON_ERROR_STOP=1` in one transaction.

## Why a subset and not the full MAIN baseline

Committing the full MAIN baseline (about 100 tables, every function, policy and grant) is an OWNER decision that is still pending (ci_validation DB-CI-PG17, risk 1). The confirmation of the MAIN-history divergences is also an owner decision: `news_canvas_schema` has a different version, and `20260923120000` and `20260730120000` are absent from MAIN history. None of that is in the repo.

The subset follows the precedent the repo already accepts: `backend/dbtest` commits hand-copied MAIN shapes in `Slice0Db.PREREQUISITOS` and `Slice1Db.MAIN_SHAPES`.

## What the CI gate covers

- The real engine: Supabase `postgres` 17.6.1.171, pinned by digest. It provides the `auth` schema and `auth.uid()`, plus the `anon`, `authenticated` and `service_role` roles.
- The MAIN shape of every object the pending set touches, loaded with zero errors tolerated.
- The pending set applied in order with `ON_ERROR_STOP=1`. Each migration's `VERIFY` block runs right after it, and every counter must be 0. An empty result or a missing block fails the gate. The one exception is `20260928100100`, which predates the VERIFY convention and is covered by the matrix below.
- Behavioural assertions: the state gate of the RPCs, onboarding and replay, deletion requests, the anon/authenticated boundaries, client guards and NO ACTION retention; Slice 3 exam runtime (start / answer / finish / abandon commands, frozen set, annulled questions, one open attempt, commands closed to clients) and its hardening (`20261008100200`: an attempt the start command did not create is not found by any command and never frozen, immutable command marker, exam-origin only, FK indexes); Slice 2 "my exams" collection read (`20261008100300`: union of valid grants and command attempts, published exams only, own rows only, keyset page, groups over the whole filtered set, closed to clients and open to `service_role`).
- The final grants/RLS matrix:
  - RLS is enabled on every table.
  - Server-only tables grant no client privilege.
  - Every SECURITY DEFINER function pins `search_path`.
  - No SECURITY DEFINER function is executable by clients, except the two MAIN RLS helpers.
  - `service_role` can execute the Slice 1 RPCs.
  - The `private` schema is closed to clients.
- Running every `ROLLBACK` block in reverse returns the catalog to the post-bootstrap state. Re-applying reproduces the same catalog, with VERIFY at 0 again. The catalog fingerprint covers columns, constraints, indexes, triggers, function signatures, flags and ACLs, policies, RLS and table ACLs; it does not cover function bodies.
- A negative control, `scripts/db-pg17-gate.test.sh`, runs in the same job. Each seeded violation must fail for its own reason:
  - a manifest line removed;
  - a missing VERIFY block;
  - a client grant (caught by the boundary assertions, the matrix and VERIFY);
  - a syntax error;
  - an incomplete rollback.

## What it does NOT cover

The complete local PG17 gate stays the stronger gate before a deploy. See `SLICE_1_PRODUCTION_GATE.md` in OposiBot.

- **Objects of MAIN outside the closure:** about 85 other tables, their functions, policies, triggers and storage/realtime. The CI gate cannot detect an interaction between a pending migration and an object it does not name.
- **The 55/55 fingerprint against `main_fingerprint.json`, and the structural schema diff** (`schemadiff.js`).
- **Drift between this subset and live MAIN.** CI cannot read MAIN, so freshness depends on the manual recapture described above.
- **Two-session concurrency.** It stays in `backend/dbtest`, which runs on embedded PostgreSQL 16.
- **REST/PostgREST and the Ktor end-to-end.**
- **Data-dependent behaviour on real rows** (the capture has none).
- **Supabase platform internals:** GoTrue migrations, storage-api and realtime.
